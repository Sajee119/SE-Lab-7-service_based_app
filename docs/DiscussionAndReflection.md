# Discussion and Reflection: Stock Management in Service-Based Architecture

## 1. Modularity

Adding stock management reinforced how modularity localises change. The entire stock feature was implemented by touching only three files — `product_service.php`, `order_service.php`, and the order handler in `app.js` — while `index.html`, `style.css`, and `auth_service.php` were untouched. Critically, the **stock validation rule lives inside the order service**, not in the front end. The browser does not decide whether stock is sufficient; it simply displays whatever the service returns. This is a deliberate architectural choice: business rules sit at the service boundary, so every consumer of the order service — a web front end, a mobile app, a future admin tool — inherits the same rule automatically. In a monolithic or front-end-heavy design, the same rule would have to be duplicated in every client, creating drift and inconsistency. From a cost perspective, localised change means lower regression risk and fewer developer-hours per feature: the stock feature was cheap to add precisely because the service boundaries already existed.

## 2. Reusability

The stock check is reusable in two senses. First, the **response contract** is generic: `status: 'error'` with a `message` field is already handled by the existing error branch in `app.js`, so the new "exceeds available stock" and "product not found" cases required no new client code beyond the alert. Designing services around stable, generic error contracts means future validation rules (e.g., maximum order size, discontinued products) can be added to the service without changing consumers. Second, the **stock field** added to the product service is now available to any consumer — the catalog page, an order form, or an inventory dashboard — at no extra cost. This illustrates the economic principle that a well-designed service interface amortises the cost of one implementation across many present and future consumers, whereas bespoke logic in a single client is paid for once and reused never.

## 3. Scalability

The stock feature highlights an important scalability consideration: stock checking is a **read-then-write** operation, and correctness depends on the check and the decrement happening atomically. In the current stateless design this is trivially safe because nothing persists, but it reveals the scaling problem real systems face. If the order service were replicated to handle load, concurrent orders could both read the same stock level and both succeed, overselling the product. Solving this requires a shared, transactional data store (a database with row locking or atomic decrement) rather than in-memory arrays — an additional cost that must be weighed against correctness and demand. Economically, this is the classic trade-off: independent scaling of the order service is only safe if state is externalised, which adds infrastructure cost but prevents the far larger commercial cost of overselling and customer dissatisfaction.

## 4. Maintenance

Maintenance benefits were evident during testing. Because stock logic is confined to `order_service.php`, I could verify all stock behaviour — sufficient stock, insufficient stock, exact-stock boundary, unknown product — by exercising one endpoint, without touching authentication or catalog code. The service's explicit error messages ("Requested quantity exceeds available stock", "Product not found") also serve as self-documenting maintenance aids, making the rule discoverable to future developers. In a monolithic design, stock logic would likely be entangled with order creation, pricing, and persistence, so any change would require understanding and retesting a larger surface. The containment of change again translates directly into cost: fewer files touched, fewer tests to rerun, less risk of breaking unrelated functionality, and shorter release cycles.

## 5. Challenges and Trade-offs

This task exposed the central weakness of the simulated design: **PHP is stateless, so the reduced stock does not persist between requests**. Each order restarts from the hard-coded inventory, and the same product can be "oversold" across separate requests. This is not a bug in the logic but a consequence of storing state in a request-scoped variable; the manual acknowledges it by instructing that a database would replace it in a real application. The trade-off is therefore between the **simplicity and zero cost** of an in-memory demonstration and the **correctness, durability, and concurrency-safety** of a persistent, transactional data store. A second challenge was integration fragility: the front end's parsing logic depends on the exact shape of the JSON response, so any change to the service contract — such as renaming `remaining_stock` — silently breaks the client unless both are updated together. This argues for treating service interfaces as versioned contracts and for defensive client code. Overall, the exercise confirms the broader economic argument of the lab: service-based architecture front-loads design and integration cost in exchange for cheaper change, reuse, and scaling later — and that investment only pays off when the system's lifespan and rate of change are large enough to amortise the overhead, and when the infrastructure (notably shared state) is funded appropriately.
